# b5: ATS初回Elapse待機とCPU/GPU描画間隔の追加分析

## 現在確認できていること

2026年11月1日13:03～13:08のb5ワンクリック計測（240秒）では、描画系列AとBの最初のサンプルが計測開始から約31.1秒後に記録された。初回Present検出のみを開始条件としていたが、実際の運転処理の開始とは一致しなかった。

描画系列A：CPU Busy平均26.50ms、GPU Busy平均2.81ms、Present間隔50ms超15件。
描画系列B：CPU Busy平均14.75ms、GPU Busy平均1.10ms、Present間隔50ms超0件。
これはCPU側の処理時間の特徴を示すものであり、特定の処理が原因であることや系列Aが運転画面であることは確定できない。

## 変更（b5専用・実走行未検証）

1. x86 ATSホストで最初のATS Elapseが正常に終了した直後、一度だけ HOST_FIRST_ELAPSE frame=1 qpc=... qpc_freq=... をbridge.logに記録し、flushする。フレームごとにディスクアクセスしない。
2. ワンクリック起動では通常権限のランチャーが正確なBVE PIDと、対応するbridge.logの絶対パスを、同一テスト用の状態ファイルで管理者計測側へ通知する。PID通知より前にログパス情報を作成し、古いログを日付順で推測しない。
3. CaptureB5Timing.ps1は最初のATS Elapse記録を確認してから、従来のPresentMon短時間プローブを開始する。描画確認ができるまで240秒の本計測は開始しない。
4. ATS初回記録を最大360秒待機。BVE終了やタイムアウト時は原因を表示して中止し、データがない場合に成功扱いをしない。ゲームは自動終了させない。
5. 計測メタデータに初回ATSの記録時刻とQPC、ログの対応を保存する。
6. AnalyzeB5CpuFrames.pyを追加し、PresentMonの各SwapChainAddressを混同せず、CPU/GPU Busy平均・95%点・最大値、50ms超の描画間隔、最大10件の長時間フレームをCSVから自動集計する。FPS/ATS比較レポートと送信/入力待ち比較レポートに加え、b5-cpu-gpu-frames.mdを出力する。

### 重要な制約

- ATSの最初のElapseはシミュレーションの開始を示すが、車両・路線の完全な読み込みや運転可能状態の保証ではない。初回Elapse後も描画が安定するとは限らない。
- BVEの実際の運転画面とPresentMonの描画系列の対応付けは未確定。
- CPU BusyがGPU Busyより大きいことだけでは、BVE本体・ATS・Windows等のどれがカクつきを起こしたかは特定できない。
- 今回の計測機能は昨日のログにある大きな遅延を解消する変更ではない。実際のFPS改善・遅延解消は未証明。
- 管理者権限はPresentMon計測のみ。公開済みb4、元の路線・車両・ATSファイル、Windows/GPU設定は変更しない。
